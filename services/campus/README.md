# Campus API

Node.js 24 built-in SQLite stores accounts, hashed sessions, wallets, a shared leaderboard and forum. `npm run dev`, `npm run preview` and `npm start` attach `/api/campus` alongside the existing schedule/news APIs. `createNewsServer` accepts an optional `campusService` for embedding/testing.

Registration accepts a student email at **stud.uust.ru** (`login`) by default, or any provider when `CAMPUS_EMAIL_DOMAINS=*` is set for testing, and a separate PocketUUST password of 15–128 characters. Existing shorter passwords still work for login. Names are 2–80 characters; emails are normalized to lowercase. New registrations remain pending until a six-digit code sent by SMTP is confirmed. Pending registrations have no user ID, wallet or session. An existing unverified user enters the original password, then confirms a code without losing the original ID, forum content, or rewards. Domain restriction plus code proves access to a mailbox, not active enrollment. No password reset or university/ISU single sign-on is configured.

Settings:

For local `npm run dev`, set `CAMPUS_TEST_EMAIL_CODE=123456` in `.env` to accept that code for registration and existing unverified accounts without sending an email. This setting is ignored unless `NODE_ENV=development`; remove it when testing real email delivery. Verified accounts log in directly without a code.

For a local test group, put the supplied `test-accounts.txt` in the project root and run `npm run seed:test-accounts` once while the site is stopped. The command inserts 128 already verified accounts, `001@stud.uust.ru` through `128@stud.uust.ru`, into the existing SQLite database without replacing forum or other users. It stops before inserting if any of those logins already exists. The credential file is ignored by Git. The mail-code secret is used only for email challenges; account passwords use salted scrypt hashes.

| Environment                                | Default / purpose                                                                            |
| ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `CAMPUS_DATA_DIR`                          | `.runtime/campus`, containing `campus.sqlite` and its WAL files                              |
| `CAMPUS_EMAIL_DOMAINS`                     | `stud.uust.ru`; exact comma-separated allowed domains, or `*` for any domain                 |
| `CAMPUS_PUBLIC_ORIGIN`                     | Optional canonical site origin; set to the external HTTPS origin behind a proxy              |
| `NODE_ENV=production`                      | Enables `Secure` cookies; production must use HTTPS                                          |
| `CAMPUS_SECURE_COOKIES=true`               | Explicitly enables `Secure` cookies                                                          |
| `CAMPUS_SMTP_HOST`, `CAMPUS_SMTP_PORT`     | SMTP host and port, usually 465 (TLS) or 587 (STARTTLS)                                      |
| `CAMPUS_SMTP_SECURE`                       | `true` for TLS on 465, `false` for required STARTTLS on 587                                  |
| `CAMPUS_SMTP_USER`, `CAMPUS_SMTP_PASSWORD` | Server-only SMTP credentials                                                                 |
| `CAMPUS_MAIL_FROM`                         | SMTP-provider-approved sender address                                                        |
| `CAMPUS_EMAIL_CODE_SECRET`                 | Persistent 32-byte secret as 64 hexadecimal characters; generate with `openssl rand -hex 32` |

`npm run dev` loads `.env` through Vite; `npm start` loads it through Node. Restart after changing settings. Without complete SMTP settings and a valid secret, registration and confirmation return 503, while existing verified login and other services continue working. Tests inject an in-memory sender; real delivery to a student mailbox requires your SMTP account and an end-to-end check. Do not commit `.env` or copy runtime SQLite files into the ZIP. Back up an existing active SQLite database using SQLite backup or stop the server before copying its WAL files. First startup migrates the schema, retains existing IDs/content, and invalidates unverified sessions.

API: `GET /auth/config` returns public domain/field settings; `POST /auth/register` returns HTTP 202 with `challengeId`, `email`, `expiresAt`, `resendAvailableAt`; `POST /auth/verify-email` accepts `challengeId` and a six-digit string `code` and returns HTTP 201 or 200 with an authenticated session. `POST /auth/resend-code` accepts `challengeId`, rotates the code and returns a new expiry. `POST /auth/login` returns HTTP 200 for verified users and HTTP 202 with a challenge for old unverified accounts. Routes use the `/api/campus` prefix. Never print codes in server logs or return them from production API.

Codes expire after 10 minutes; a registration attempt lives for at most 30 minutes. Resend cooldown is 60 seconds and invalidates the prior code. Five wrong attempts block a challenge; mail sends and code guesses also have per-address and per-IP limits retained in SQLite. Codes are stored as HMACs bound to the challenge and secret; pending passwords are stored only as hashes. New passwords use scrypt N=131072/r=8/p=1 with a random 16-byte salt; the old N=32768 format remains readable and upgrades on a successful verified login. At most two expensive password derivations run at once. Sessions expire after 14 days; session tokens have 256 random bits and are stored as SHA-256 hashes. Cookies use HttpOnly and SameSite=Lax. Writes require JSON, reject foreign origins, and cap input at 32 KiB. IP limits use the direct connection address; behind a proxy configure upstream IP limits too. Arbitrary client-supplied coin amounts never influence rewards.

Reading a real seed/runtime news ID awards 3 once per account; saving awards 1 once. A successful nonempty route supported by the shared navigation graph awards 2 per account/graph path/Ufa day. Input keys use `from>to:inside` or `from>to:outside`; reward identity hashes the actual directed graph edges. Room labels on the same floor that produce the same path share one reward, and outdoor permission shares that reward when it does not alter the path. Paths with zero graph edges receive no reward. The navigation graph is schematic and cannot certify the existence of an individual room. Floors 1–5 use lifetime earned thresholds 0/30/80/150/250; spending does not lower floors.

Games issue a random account-owned challenge, require at least 40 reported clicks and five elapsed seconds, expire after 15 minutes and award 25 at most once per Ufa day. The server blocks replay/foreign challenges, but cannot independently prove physical clicks from a browser. The hoodie action atomically spends 500 and creates a **demo receipt**; real merchandise delivery is not connected.

Forum reading is public; writing requires an account. Titles are 5–120 characters, topics 10–4000 and replies 3–3000. The first three topics/day earn 5 forum points each, and first ten replies/day earn 2; further posts remain allowed without points. Identical existing own topics/replies within a Ufa day return 409. Deleted content keeps its reward record and ID, so removing a post never resets daily reward caps. Forum points are separate from spendable coins. On the user's next access, each finished month's points settle exactly once into `floor(points/50)` demo tickets; monthly remainder does not carry over. No real ticket issuance or live event integration is connected.

Forum topics use cursor pagination: `GET /forum/topics?beforeId=N&limit=50` returns newest topics in descending ID order and `{topics,total,hasMore,nextBeforeId}`. A topic detail request `GET /forum/topics/:id?beforeReplyId=N&limit=50` returns the newest reply page in chronological order and `{topic,replies,totalReplies,hasMore,nextBeforeReplyId}`. Omit the cursor for the newest page, use the returned cursor to request older pages, and prepend older replies in the client. Default/max page size is 50; allowed sizes are 1–50. End-of-history cursors are null. Invalid cursors and sizes return 400.

Forum interactions and filtering are documented in [../../docs/FORUM.md](../../docs/FORUM.md). Schema version 2 adds topic/reply likes, private bookmarks, reply references and deletion markers automatically. Existing accounts and forum IDs survive migration. The forum query/storage code lives in `forum.mjs`; the existing service keeps authentication, rate limits, origin checks and rewards.

Tests: `node --test services/campus/tests/*.test.mjs`. Runtime data is private; omit `.runtime`, credentials and internal plans from source archives. Back up the database with SQLite-aware tooling, or stop the service before copying the database and WAL files.
